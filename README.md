# Чек на удачу

Небольшое веб-приложение промо-акции: покупатель регистрирует чек, модератор проверяет его в админке. Python, Django 5.2, PostgreSQL 16, Docker.

## Как запустить

Нужен Docker с Compose. Больше ничего ставить не надо.

```bash
git clone https://github.com/NBx03/lucky-receipt.git
cd lucky-receipt
docker compose up --build
```

Сайт откроется на http://localhost:8000. Миграции и сборка статики выполняются при старте контейнера, `.env` создавать не нужно: настройки по умолчанию лежат в `.env.example`. Если хочется поменять значения, скопируйте его в `.env` и правьте там, он перекроет примеры.

Модератора нужно завести один раз:

```bash
docker compose exec web python manage.py createsuperuser
```

Админка: http://localhost:8000/admin/. Обычный пользователь с флагом staff тоже подойдёт, но ему нужно выдать права на модель «чеки».

Покупатель регистрируется на http://localhost:8000/accounts/signup/ и после этого сразу попадает в личный кабинет.

Тесты:

```bash
docker compose run --rm web python manage.py test
```

### Настройки

Всё задаётся переменными окружения, примеры в `.env.example`.

| Переменная | Что это |
|---|---|
| `SECRET_KEY` | секретный ключ Django |
| `DEBUG` | `1` включает режим отладки, по умолчанию `0` |
| `ALLOWED_HOSTS` | допустимые хосты через запятую |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_HOST`, `POSTGRES_PORT` | подключение к базе |
| `PROMO_TIMEZONE` | часовой пояс акции |
| `PROMO_START_DATE`, `PROMO_END_DATE` | первый и последний день акции, формат `ГГГГ-ММ-ДД`, оба включительно |

В примере акция идёт весь 2026 год. Если начало позже конца, приложение не стартует и говорит об этом. Минимальная сумма чека, 1000 ₽, лежит константой в `receipts/forms.py`.

Имя и пароль базы применяются при первом создании тома. Если поменяли их после запуска, выполните `docker compose down -v`, но это удалит данные.

## Что сделано

- Регистрация и вход на `django.contrib.auth`. Страницы входа и регистрации простые, в стиле остального сайта.
- Модель чека: ФН, ФД, ФП, дата и время покупки, сумма, статус, причина отказа, пользователь, дата регистрации.
- Форма регистрации чека с проверкой на сервере: период акции, сумма от 1000 ₽, уникальность ФН + ФД + ФП. Новый чек всегда получает статус «на проверке». Статус и пользователя из запроса сервер не принимает.
- Отправка формы через `fetch`. Перед отправкой JS проверяет те же правила и показывает ошибки рядом с полями. Ответ сервера тоже показывается на странице: успех отдельной карточкой, ошибки красным.
- Личный кабинет: свои чеки от новых к старым, по 10 на странице. Кнопка «Зарегистрировать чек» ведёт на форму. Если чеков нет, показывается пустое состояние.
- Админка: модератор видит чеки, фильтрует по статусу, ищет по реквизитам и пользователю, меняет статус. При отказе причина обязательна.
- `GET /api/receipts/`: чеки текущего пользователя в JSON.
- Вёрстка по макету из Figma, на 375px ничего не уезжает и горизонтального скролла нет.
- `docker compose up` поднимает приложение вместе с Postgres.

Структура: `config/` настройки проекта, `receipts/` единственное приложение (модель, форма, представления, админка, тесты), `templates/` и `static/` шаблоны, стили и скрипты.

## Что сверх задания

- Тесты: 41 штука, на форму регистрации, модель, кабинет, API и выгрузку. Лежат в `receipts/tests/`.
- Поле «Строка из QR-кода» над формой. Принимает `t=...&s=...&fn=...&i=...&fp=...` (или ссылку с такими параметрами) и заполняет поля. Если что-то не нашлось, пишет, чего именно. Разбор в `static/js/qr.js`.
- Выгрузка принятых чеков в CSV: в списке чеков в админке выбираете чеки и применяете действие «Выгрузить принятые чеки в CSV». Попадают только принятые из выбранных. Файл в UTF-8 с BOM, разделитель `;`, чтобы русский Excel открыл его без возни.

## Спорные места

**Повторная отправка отклонённого чека.** Можно. Отклонённый чек выпадает из проверки уникальности, и такой же чек регистрируется заново как новая запись, старая остаётся вместе с причиной отказа. Чек «на проверке» или принятый второй раз не принимается, даже если его подаёт другой пользователь. В сообщении «Этот чек уже зарегистрирован» не сказано, чей он. Уникальность держится на частичном индексе в базе, поэтому два одновременных запроса тоже не создадут дубль, второй получит то же сообщение, а не ошибку 500.

**Границы периода и часовой пояс.** Период считается в часовом поясе акции (`PROMO_TIMEZONE`), оба дня включительно: с 00:00 первого дня до 23:59 последнего. Время на чеке читается как местное время акции. Пояс пользователя не определяется: он вводит дату и время так, как они напечатаны на чеке, а сервер и JS сравнивают их с периодом одним и тем же способом. Покупку в будущем отклоняем. В кабинете и в API даты показываются в том же поясе.

**Реквизиты чека.** ФН это ровно 16 цифр, ФД и ФП от 1 до 10 цифр. Хранятся строками, чтобы не терять ведущие нули. При этом `0042` и `42` считаются одним документом: нули у ФД и ФП отбрасываются перед сохранением, иначе дубль обходился бы припиской нуля.

**Сумма.** Ровно 1000 ₽ подходит. Принимается и точка, и запятая, пробелы внутри числа игнорируются (`1 500,50`), знаков после запятой не больше двух. Хранится как `Decimal`, в API отдаётся строкой, чтобы клиент не превратил деньги в `float`.

**Порядок чеков.** От новых к старым по дате покупки, потому что именно её пользователь видит в списке. Если даты совпадают, выше тот, кто зарегистрирован позже.

**Причина отказа.** Для статуса «отклонён» обязательна. При любом другом статусе очищается, чтобы в кабинете не осталось старой причины у принятого чека. Модератор не может вернуть отклонённый чек «на проверку» или принять, если такой же чек уже зарегистрирован заново: админка скажет, что он уже есть.

**API.** Выборка строится от текущего пользователя, параметры запроса на неё не влияют. Модератор через API тоже видит только свои чеки. Без входа отдаётся 403 с JSON, а не перенаправление на страницу входа.

**Макет.** Макета для мобильной версии нет, на узких экранах таблица превращается в карточки. Шрифт, судя по макету, Mulish, подключён с Google Fonts. Цвета снимал со скриншотов макета, оттенки текста у статусов «на проверке» и «принят» сделал немного темнее, иначе они плохо читаются.

## Работа с ИИ

Я писал приложение вместе с Claude Code, слоями: каждый слой он делал отдельно, я читал код, просил объяснить непонятное и коммитил сам.

**Где помог больше всего.** Вёрстка по макету и мелочи вокруг: подбор цветов по скриншотам, адаптив, разбор QR-строки. Ещё он быстро нашёл типичные ловушки задания: у `django.contrib.auth` нет страницы регистрации, `login_required` на JSON-ручке отдаёт редирект вместо JSON, при запуске в Docker приложение стартует раньше базы.

**Что выдал неправильно и как заметил.**
- Уникальный индекс с условием (чтобы отклонённый чек можно было подать заново) Django сам не проверяет, если поля `status` нет в форме, а в форме покупателя его нет. Проверка дубля тихо пропускалась бы. Поймал на ручной проверке в консоли, дубль теперь проверяется явно в `Receipt.clean()`.
- В первой версии дубль в админке выдавал два сообщения, одно из которых техническое. Тоже увидел при ручном прогоне, исправил переопределением `validate_constraints`.
- Сумма `1e5` проходила как 100 000, потому что `Decimal` разбирает экспоненту. Заметил, когда перебирал мусорные значения вручную, теперь отсекается регуляркой.
- В тесте на границы периода «текущее время» стояло раньше конца акции, и последний день периода оказывался «будущим». Тест падал, хотя код был верный. Разобрался и подвинул дату в тесте.
- Один раз сборка образа упала из-за сети, а проверки шли по старому образу. Заметил по тому, что маршрута, который только что добавил, не было.

**Что бы переписал, будь больше времени.**
- Правила проверки лежат в двух местах: на сервере и в JS. Сейчас их держат в соответствии вручную. Лучше отдавать правила с сервера или генерировать из одного описания.
- Добавил бы тесты на JS и на разбор QR, сейчас они проверены только руками.
- Сделал бы постраничный вывод в API и ограничение числа запросов на регистрацию чеков.
- Стили лежат одним файлом, при росте проекта их стоило бы разбить по страницам.
- Выгрузку CSV в админке сделал бы отдельной кнопкой на все принятые, а не действием над выбранными.
